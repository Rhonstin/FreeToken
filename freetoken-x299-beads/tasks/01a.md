# 01a. Зафіксувати X299 topology і реальний bandwidth — контракт і fixtures

Версія плану: 2. Стара задача: 01.

## Вхідні умови

lscpu JSON; sysfs topology; MemAvailable; populated DIMM sizes і configured speed; GPU BDF/link під load.

## Контракт

Hardware fingerprint без hostname/serial; separate observed/capability fields.

## Покрокове виконання

1. Зібрати inputs нижче; невідомі поля залишити null із reason, не підставляти guesses.
2. Прочитати поточні symbols у вказаних файлах; порівняти з baseline SHA. За drift оновити contract, не застосовувати старі hunks.
3. Створити contract.json за CONTRACTS.md: scope, baseline, fields, invariants, cases, commands, expected outcomes.
4. Описати кожний negative case як fixture: given/when/then, exact assertions; valid/invalid cases розділити.
5. Зібрати baseline/reproduction evidence до production code edit. Hardware відсутній — заблокувати лише необхідну hardware частину.
6. Зафіксувати bounded candidate set, numerical tolerances і performance metric до вимірів. Передати артефакти задачі b.

## Обов’язкові негативні сценарії

- lscpu не містить SKU.
- cpuset має менше cores.
- немає DMI permission.
- DIMM map неповний.
- link Gen1 у idle і Gen3 у load.

## Stop conditions

Не запускати ISA за marketing name. Невідомий channel count лишити unknown; planning може продовжуватися на measured bandwidth. Відсутній exact CPU блокує CPU-specific preset.

## Артефакти

У `evidence/x299/01a/`: contract.json, commands.json, result.json і raw logs. Для a result.outcome=contract_ready; для b implemented/no_change/blocked. Actual raw measurement paths мають існувати. Усі статуси в Beads.

## Конкретні команди

```bash
bd show <actual-bead-id>
uv run pytest --collect-only -q <existing-test-paths-from-contract>
uv run pytest -q <existing-test-paths-from-contract> -m "not slow"
```

Кутові параметри — не runnable literals: задача a замінює їх реальними знайденими шляхами. Для inventory/benchmark-only задач pytest=N/A із reason, а acceptance перевіряється даними; це не test passed. Повні executable argv зберігати в commands.json.

## Критерій закриття цієї фази

Усі fixtures мають expected results, inputs перевірені, contract і baseline артефакти існують; production code не змінений.

# 01. Зафіксувати X299 topology і реальний bandwidth

## Робота

Зібрати exact i7 SKU, cores/SMT/ISA, motherboard/BIOS, DIMM sizes/slots/configured speed і реально активні канали. 104 GB не доводять quad-channel; 2133 трактувати як заявлені DDR MT/s до перевірки. Записати OS/driver/CUDA, PCIe negotiated speed/width під навантаженням, RAM available, storage model/interface і filesystem. Виміряти CPU read bandwidth, pinned H2D/D2H, expert gather та CPU+PCIe overlap через наявний ft bench bw.

## Критерії приймання

hardware.json і raw reports містять actual дані та unknown. PCIe очікування перевірене під load. Benchmark не займає всю RAM. Немає автоматичних BIOS/overclock/ASPM/IOMMU/governor змін. CPU flags не виведені лише з назви X299.
