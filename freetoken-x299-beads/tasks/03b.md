# 03b. Розширити наявний benchmark під decode latency — виконання та приймання

Версія плану: 2. Стара задача: 03.

## Вхідні умови

paired BF16/no-spec baseline; actual tokenizer counts; server/client timestamps.

## Контракт

report schema_version; raw rows immutable; numerator/denominator documented; no fabricated per-token timing.

## Покрокове виконання

1. Прочитати завершений contract задачі a та перевірити evidence SHA/hardware fingerprint.
2. Виконати базову діагностику/experiment за contract. Для optimization без bottleneck evidence завершити no-change ADR, не писати speculative code.
3. Змінити лише узгоджені interfaces/files. Інший subsystem виявився необхідним — створити blocker bead, не розширювати scope мовчки.
4. Запустити positive і negative fixtures із задачі a та релевантні існуючі regression tests. Для bug спочатку red на baseline, потім green.
5. Запустити paired uninstrumented A/B за RUNBOOK.md; raw rows не редагувати. OOM/error/skipped окремо, а не в mean.
6. Перевірити rollback до baseline/default і повторний запуск. Заповнити result.json, no-change ADR за потреби.
7. Закрити bead тільки після GATES.md. У handoff вказати exact command, exit code, artifact SHA, limitations і actual next ready ID.

## Обов’язкові негативні сценарії

- SSE chunk містить кілька tokens.
- EOS завершує раніше.
- timeout.
- сервер падає.
- output порожній.
- usage відсутній.

## Stop conditions

Не змішувати incomplete/error rows із successful. Token timestamps тільки коли server надає їх; client chunk latency окремо.

## Артефакти

У `evidence/x299/03b/`: contract.json, commands.json, result.json і raw logs. Для a result.outcome=contract_ready; для b implemented/no_change/blocked. Actual raw measurement paths мають існувати. Усі статуси в Beads.

## Конкретні команди

```bash
bd show <actual-bead-id>
uv run pytest --collect-only -q <existing-test-paths-from-contract>
uv run pytest -q <existing-test-paths-from-contract> -m "not slow"
```

Кутові параметри — не runnable literals: задача a замінює їх реальними знайденими шляхами. Для inventory/benchmark-only задач pytest=N/A із reason, а acceptance перевіряється даними; це не test passed. Повні executable argv зберігати в commands.json.

## Критерій закриття цієї фази

Усі критерії нижче та GATES.md пройдені; no-change має виміри й причину; missing hardware не вважається no-change.

## Детальна постановка батьківської задачі

# 03. Розширити наявний benchmark під decode latency

## Робота

Розширити benchmarks/bench_kv_quant.py і bench_decode_moe.py, не створювати конкуруючий framework. Основна метрика — committed output tokens/s одного запиту, TPOT та p50/p95 inter-token latency; TTFT окремо. Context 4K/16K/32K, 64K лише після fit; outputs 256/512, concurrency 1 основна, 2/4 secondary. Greedy fixed seeds, однакові tokenized prompts, мінімум 3 paired repeats після warmup, A/B або ABBA.

## Критерії приймання

JSON містить actual prompt/output token counts, server phase times і client times. SSE chunk не вважається token; speculative proposed tokens не рахуються output. Холодні load/JIT/prefix винесені окремо. Baseline команди відтворювані. PPL позначений blocked до незалежного teacher-forcing harness: server logprobs зараз немає.
