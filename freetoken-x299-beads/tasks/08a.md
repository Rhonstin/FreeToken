# 08a. Виправити ключі й актуальність hardware profile — контракт і fixtures

Версія плану: 2. Стара задача: 08.

## Вхідні умови

existing profile schema і _usable_profile behavior; actual CPU/RAM/PCIe fingerprint.

## Контракт

Versioned schema, atomic write; compatibility matcher pure/CPU-testable; explain rejection reason.

## Покрокове виконання

1. Зібрати inputs нижче; невідомі поля залишити null із reason, не підставляти guesses.
2. Прочитати поточні symbols у вказаних файлах; порівняти з baseline SHA. За drift оновити contract, не застосовувати старі hunks.
3. Створити contract.json за CONTRACTS.md: scope, baseline, fields, invariants, cases, commands, expected outcomes.
4. Описати кожний negative case як fixture: given/when/then, exact assertions; valid/invalid cases розділити.
5. Зібрати baseline/reproduction evidence до production code edit. Hardware відсутній — заблокувати лише необхідну hardware частину.
6. Зафіксувати bounded candidate set, numerical tolerances і performance metric до вимірів. Передати артефакти задачі b.

## Обов’язкові негативні сценарії

- same GPU different CPU.
- changed threads.
- same name different BDF/link.
- missing fields.
- unknown schema.
- NaN bandwidth.

## Stop conditions

Старий профіль — informational only, доки validation не доведе compatibility. Explicit override не означає valid measured data.

## Артефакти

У `evidence/x299/08a/`: contract.json, commands.json, result.json і raw logs. Для a result.outcome=contract_ready; для b implemented/no_change/blocked. Actual raw measurement paths мають існувати. Усі статуси в Beads.

## Конкретні команди

```bash
bd show <actual-bead-id>
uv run pytest --collect-only -q <existing-test-paths-from-contract>
uv run pytest -q <existing-test-paths-from-contract> -m "not slow"
```

Кутові параметри — не runnable literals: задача a замінює їх реальними знайденими шляхами. Для inventory/benchmark-only задач pytest=N/A із reason, а acceptance перевіряється даними; це не test passed. Повні executable argv зберігати в commands.json.

## Критерій закриття цієї фази

Усі fixtures мають expected results, inputs перевірені, contract і baseline артефакти існують; production code не змінений.

## Робота

Аудит _usable_profile: поточний reader переважно перевіряє GPU name і per-GPU path. Додати versioned fingerprint CPU SKU/ISA/thread-affinity, RAM topology/speed, PCIe BDF/link, driver/runtime, quant format, expert shape/top-k і concurrency regime. Не брати профіль іншої RAM/CPU конфігурації лише через ту саму 3090. Звірити upstream #278/#37/#38/#39 до реалізації.

## Критерії приймання

Unit tests відхиляють stale або incompatible profiles, legacy migration описана. Профіль не містить serial numbers або секретів. Measured overlap уже існує — розширити його, не дублювати. Fallback conservative і пояснений у логах.
