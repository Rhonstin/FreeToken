# 15a. Приймання існуючого MTP: correctness і повний cost — контракт і fixtures

Версія плану: 2. Стара задача: 15.

## Вхідні умови

draft checkpoint schema, budget, existing spec unit tests, no-spec reference.

## Контракт

committed prefix invariant across host tokens/device tokens/KV/recurrent state/counters.

## Покрокове виконання

1. Зібрати inputs нижче; невідомі поля залишити null із reason, не підставляти guesses.
2. Прочитати поточні symbols у вказаних файлах; порівняти з baseline SHA. За drift оновити contract, не застосовувати старі hunks.
3. Створити contract.json за CONTRACTS.md: scope, baseline, fields, invariants, cases, commands, expected outcomes.
4. Описати кожний negative case як fixture: given/when/then, exact assertions; valid/invalid cases розділити.
5. Зібрати baseline/reproduction evidence до production code edit. Hardware відсутній — заблокувати лише необхідну hardware частину.
6. Зафіксувати bounded candidate set, numerical tolerances і performance metric до вимірів. Передати артефакти задачі b.

## Обов’язкові негативні сценарії

- accept 0/partial/all.
- EOS inside proposal.
- max length.
- stochastic reject.
- cancellation.
- QSA/GDN/PLE rollback.

## Stop conditions

Якщо any state oracle fails — MTP off і bug bead. No speed acceptance before correctness.

## Артефакти

У `evidence/x299/15a/`: contract.json, commands.json, result.json і raw logs. Для a result.outcome=contract_ready; для b implemented/no_change/blocked. Actual raw measurement paths мають існувати. Усі статуси в Beads.

## Критерій закриття цієї фази

# 15. Приймання існуючого MTP: correctness і повний cost

## Робота

MTP head/driver уже є: не створювати заново. Перевірити точний checkpoint, dedicated BF16 draft expert banks і додаткові RAM/VRAM/PCIe витрати. MTP off vs depths 1/2/3, adaptive off спочатку. Exact verify/commit/rollback тестувати для greedy/stochastic, rejection всіх/частини/жодного, EOS, stop і length bounds. QSA/GDN/PLE state повинен відповідати committed prefix.

## Критерії приймання

Звіти: draft time, target verify time, accepted drafts, emitted committed tokens, rollback/replay time, expert traffic та memory. Greedy parity і stochastic verification invariants. Не вважати acceptance rate доказом speedup. Якщо fit/correctness gate не пройдено — MTP залишається вимкнений.
