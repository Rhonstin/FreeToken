## Вхідні умови

all evidence reports, chosen configuration, no-change ADR dispositions.

## Контракт

Final report joins exact run IDs; baseline and optimized reproducible; one rollback recipe tested.

## Покрокове виконання

1. Зібрати inputs нижче; невідомі поля залишити null із reason, не підставляти guesses.
2. Прочитати поточні symbols у вказаних файлах; порівняти з baseline SHA. За drift оновити contract, не застосовувати старі hunks.
3. Створити contract.json за CONTRACTS.md: scope, baseline, fields, invariants, cases, commands, expected outcomes.
4. Описати кожний negative case як fixture: given/when/then, exact assertions; valid/invalid cases розділити.
5. Зібрати baseline/reproduction evidence до production code edit. Hardware відсутній — заблокувати лише необхідну hardware частину.
6. Зафіксувати bounded candidate set, numerical tolerances і performance metric до вимірів. Передати артефакти задачі b.

## Обов’язкові негативні сценарії

- stale fingerprint.
- dirty changes missing hash.
- missing raw samples.
- incomplete test.
- sustained throttling.
- rollback command fails.

## Stop conditions

No release/preset label validated if mandatory tests skipped. No-change допустимий тільки з evidence; unknown=blocked.

## Артефакти

У `evidence/x299/20a/`: contract.json, commands.json, result.json і raw logs. Для a result.outcome=contract_ready; для b implemented/no_change/blocked. Actual raw measurement paths мають існувати. Усі статуси в Beads.

## Конкретні команди

```bash
bd show <actual-bead-id>
uv run pytest --collect-only -q <existing-test-paths-from-contract>
uv run pytest -q <existing-test-paths-from-contract> -m "not slow"
```

Кутові параметри — не runnable literals: задача a замінює їх реальними знайденими шляхами. Для inventory/benchmark-only задач pytest=N/A із reason, а acceptance перевіряється даними; це не test passed. Повні executable argv зберігати в commands.json.

## Критерій закриття цієї фази

Усі fixtures мають expected results, inputs перевірені, contract і baseline артефакти існують; production code не змінений.

## Детальна постановка батьківської задачі

# 20. Профілі X299/3090 і фінальний regression campaign

## Робота

Інтегрувати тільки зміни з виміряним виграшем; speculative optimization tasks можуть завершитися documented no-change. Повний A/B current main vs best-known config vs optimized branch. Публікувати measured presets 4K/16K/32K і optional 64K із exact checkpoint/hardware fingerprint. Не застосовувати generic preset до всіх i7/X299. Повернення до baseline одним documented command.

## Критерії приймання

Мінімум 3 paired repeats, sustained >=15 min на фіналі, power/temp/clocks і p95. Пропонований accept для code changes: >=5% median committed tok/s понад noise, <=5% p95 regression, без correctness failures; інакше experimental/no-change. Quality corpus і correctness gates зафіксовані до tuning. No OOM/swap stalls у declared workloads. README містить фактичні результати, не прогноз tokens/s.
